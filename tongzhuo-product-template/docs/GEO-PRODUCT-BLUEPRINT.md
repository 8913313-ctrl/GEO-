# 桐灼 GEO 运营产品蓝图

本文档定义桐灼 GEO 运营产品的统一形态。它不是展示页说明书，而是一个可以复制交付、持续升级、按客户配置重建的产品蓝图。

## 1. 产品定义

桐灼 GEO 运营产品 = `GEOFlow 主后台 + AI 友好官网 + 本地发布执行器 + GEO 引擎层 + 客户交付模板`

核心目标只有一个：

> 让服务型企业拥有一套可验证、可生产、可分发、可复采、可交付的 GEO 获客系统。

## 2. 产品边界

### 保留的主系统

- `GEOFlow / Laravel` 作为唯一主后台
- 官网 CMS 负责页面、栏目、FAQ、资讯、联系方式
- 内容中心负责文章、问题、素材、模板
- GEO 运营后台负责诊断、问题地图、行动方案、采样、归因
- 分发管理负责渠道任务、平台结果回写、发布队列
- 客户项目负责交付、验收、健康度、续约证据

### 不再复制的部分

- 不再复制第二套独立管理后台
- 不再把 `GEORank` 当成客户可见主后台
- 不再把平台账号、Cookie、验证码、浏览器 Profile 放进服务器交付物
- 不再把公开网站做成纯展示页

## 3. 产品主循环

```mermaid
flowchart LR
    A["企业资料 / 官网 / 业务事实"] --> B["事实底座"]
    B --> C["问题地图"]
    C --> D["证据内容"]
    D --> E["官网 CMS + AI 入口"]
    E --> F["分发管理 + 发布执行"]
    F --> G["AI 采样 + 平台回写"]
    G --> H["线索 / 归因 / 复盘"]
    H --> C
```

这个闭环决定了产品不是“做完网站就结束”，而是“内容、平台、线索、证据一起滚动”。

## 4. 三层产品结构

### 第一层：前台可见层

- 企业官网
- 行业资讯
- FAQ / 问题地图
- 联系我们
- 案例、团队、资质、问题页

### 第二层：运营中台层

- GEO 诊断
- 问题机会
- 行动方案
- AI 问答测试
- 分发任务
- 线索管理
- 客户项目

### 第三层：执行与引擎层

- `GeoEngineManager`
- `local / georank` 切换
- 本地规则兜底
- 远程增强诊断
- Windows 本地发布执行器

## 6. 核心数据契约

### 6.1 事实底座

事实底座不是知识库摘要，而是可引用的业务事实表。

必须包含：

- 企业实体
- 产品 / 服务
- 案例 / 客户
- 资质 / 荣誉
- 来源
- 更新时间
- 可信等级
- 允许表达 / 禁用表达

### 6.2 问题地图

问题地图不是单条问题，而是 AI 搜索意图单元。

必须包含：

- 问题簇
- 父问题 / 追问链
- 查询重写
- 对应页面 / 文章 / FAQ
- 覆盖状态
- 平台适配
- 竞品对照

### 6.3 证据内容

文章和 FAQ 都是证据页，必须满足：

- 开头直接回答
- 有事实、数字、案例或来源
- 有步骤、对比、边界
- 有更新时间
- 不写未核实事实

### 6.4 AI 采样

AI 采样记录必须保留：

```text
platform, surface, prompt_id, run_id, model_version, sampled_at,
mention, recommendation, rank, citations, competitor_mentions, answer_accuracy
```

### 6.5 归因

归因不能只看点击。

要同时看：

- 品牌出现率
- 推荐率
- 引用准确率
- 引用召回率
- 线索转化

## 7. 官网 CMS 的产品标准

官网不是静态展示页，而是 AI 可读的内容容器。

官网必须具备：

- 可编辑页面
- 可编辑模块
- 可编辑导航
- 可编辑 FAQ
- 可编辑行业资讯
- 可编辑联系表单
- `robots.txt`
- `sitemap.xml`
- `feed.xml`
- `llms.txt`
- `llms-full.txt`
- Schema / JSON-LD

官网内容必须支持：

- 搜索引擎抓取
- AI 抓取
- 资讯发布
- 证据页承载
- 线索转化

## 8. 发布助手的产品标准

发布助手属于 GEOFlow 的一部分，不是独立第二后台。

必须支持：

- 先在后台建任务
- 再由本地执行器登录平台
- 登录状态仅保存在本地
- 任务状态回写后台
- 失败自动降级为草稿或人工确认

推荐策略：

- 优先稳定少数平台
- 再逐步扩大平台目录
- 允许多选平台发布
- 允许平台能力差异化配置

## 9. 客户交付包

每个客户都应能生成标准化交付物：

- `LaunchPad`
- `Evidence Index`
- `Launch Readiness`
- `Health Scorecard`
- `Project Dossier`
- `Operations Evidence Pack`
- `Support Bundle`
- `Operations Bundle`

这些交付物的作用不是“存档”，而是让产品可以：

1. 复制到下一个客户
2. 给客户看清楚交付内容
3. 让运维和续约有证据

## 10. GEORank 接入方式

GEORank 只作为增强引擎，不替换主后台。

接入方式：

- `GeoEngineManager` 统一调度
- `local` 作为保底规则引擎
- `georank` 作为增强引擎
- 失败自动回退本地规则

GEORank 适合增强：

- 网站诊断
- AI 问答测试
- 问题扩展
- 行动方案

不适合做：

- 客户主后台
- 官网管理台
- 交付模板主入口

## 11. 产品分期

### 阶段 1：可用闭环

目标：能发布、能诊断、能分发、能回写。

验收：

- 官网可编辑
- 文章可发布
- 问题可生成
- 任务可分发
- 本地执行器可回写

### 阶段 2：成熟产品

目标：后台具备成熟企业系统体验，客户可独立看懂；产品以一企业一部署交付，不提供客户可见的租户切换或公有云订阅流程。

验收：

- 菜单清晰
- 内容和 GEO 分区明确
- 线索、项目、交付、日志可追踪
- 业务与技术分层一致

### 阶段 3：方法增强

目标：接入 GEORank，形成更强的诊断和采样。

验收：

- `local / georank` 可切换
- AI 采样有平台字段
- 30/60/90 天方案能绑定证据
- 归因数据可复盘

### 阶段 4：可复制销售

目标：一键形成客户交付包。

验收：

- 可生成客户配置
- 可生成正式交付包
- 可生成运营档案
- 可生成续约证据包

## 12. 成熟产品的判定标准

一个成熟的可复制产品，不看“页面多不多”，看下面 8 条：

1. 有统一主后台
2. 有可编辑官网
3. 有事实底座
4. 有问题地图
5. 有证据页生产
6. 有分发回写
7. 有归因和复盘
8. 有标准化交付包

如果这 8 条都具备，它才是产品；否则只是几个页面和几个脚本。
