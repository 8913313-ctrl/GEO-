# 系统架构（0.5 私有化生产底座）

> 本文同时保留 0.4 页面与业务规则，新增内容标记为“生产底座”。当前工程已经可以作为单企业私有化部署的运行基线；尚未接入的官网 CMS、效果监测采样和完整平台适配器仍按本文末尾的交付边界分阶段实施。

## 生产底座当前实现

```text
浏览器 / 本地发布助手
          │ HTTPS + Cookie Session / 设备 Token
          ▼
Node HTTP API（当前可运行基线）
  ├─ 首次管理员初始化、登录、登出、CSRF
  ├─ admin / operator / reviewer / viewer 权限
  ├─ 工作区保存、SQLite 乐观锁和修订历史
  ├─ 成员管理与审计日志
  ├─ 模型供应商配置（API Key AES-256-GCM 加密）
  ├─ 企业知识库（版本、审核、分块、embedding、混合检索、引用）
  ├─ 发布器配对、心跳、账号组、任务和结果
  └─ /health/live、/health/ready、/api/v1/auth/status
          ▼
SQLite（WAL + 外键 + 迁移）
  ├─ users / sessions
  ├─ workspace_state / workspace_revisions / business_records
  ├─ knowledge_libraries / knowledge_documents / knowledge_document_versions
  ├─ knowledge_chunks / knowledge_index_jobs / knowledge_retrieval_runs
  └─ audit_logs

客户 Windows 电脑
  └─ 本地发布助手（Token/设备密钥仅以摘要形式留在服务端）
```

生产底座与页面演示使用同一个工作区状态模型，浏览器缓存只作为服务暂时不可用时的容错，不再作为正式数据源。服务器端 API 是登录、权限、版本冲突、审计和发布门禁的最终裁决点。

## 产品定位

本产品面向购买服务的企业客户，每个客户独立部署一套服务器端系统。客户在浏览器中完成日常 GEO 运营，在自己的 Windows 电脑上管理内容平台登录态。企业知识是写作的事实底座，不是独立于内容生产的资料页面；写作智能体是可复用的写作策略，不是绕过知识权限的另一个知识入口。内容生产同时支持按选题计划批量生产与 AI 创作台直接起稿，两条通道使用同一套知识、版本、风控和审核门禁。

本项目的 Node.js 私有化后台是唯一管理后台；GEORank 仅作为内部拓词和低频站点诊断能力，不向客户暴露第二套后台。

## 客户与租户隔离

私有部署默认采用“一客户一部署”，但正式数据模型仍统一保存 `tenant_id`，避免后台任务、对象存储和未来托管版出现跨客户数据泄漏。

- HTTP 请求由域名、登录用户和设备令牌确定租户，控制器不能接受前端传入的任意 `tenant_id` 作为可信范围。
- 所有业务表、关联表、审计记录和唯一索引都包含 `tenant_id`；ORM 使用全局租户作用域，跨租户外键在服务层与数据库约束中同时校验。
- 队列任务、定时任务和本地助手任务必须携带并恢复租户上下文；缺少租户上下文时直接失败，不能使用系统默认租户。
- 对象存储使用独立桶或租户前缀，向量索引使用独立 collection / namespace，Redis 缓存、锁、幂等键和队列路由都带租户前缀。
- 模型调用、RAG 检索、监测采样、导出和日志查询只能使用当前租户数据；平台运维跨租户访问必须显式授权并写入审计日志。

## 两条业务流程

### 首次建档

```text
上传文件 / 手动输入企业资料
→ GEOFlow 生成企业知识初稿
→ 人工校验、修订和确认公开范围
→ 发布到文档库或问答库
→ 建立租户隔离的 RAG 索引
→ 绑定企业公共知识与业务线默认知识包
→ 供官网、内容计划、写作和审核共同引用
```

GEOFlow 已有资料输入、AI 初稿、校验、修订和发布知识库的基础流程。0.4 演示中的四步建档向导、资料完成度、结构化企业档案、文档库/问答库产品分类、业务线知识包以及产品/案例/FAQ 实体属于新增产品能力。

### 日常运营闭环

```text
企业知识（唯一事实来源）
├─ 选题中心（业务线、关键词、问题词库、选题库、内容计划）
│    └─ 内容计划继承业务线默认知识包，选择智能体，可选填写预计适配平台写作提示并冻结计划快照
└─ AI 创作台（业务线、主题、智能体和本次知识范围）
     └─ WritingWorkspace 冻结直接创作上下文，不伪造内容计划
→ 内容生产（按计划或工作区知识边界检索、生成并冻结 generationSnapshot）
→ 证据引用、风控、人工审核和文章版本冻结
→ 发布运营（选择一个账号组，勾选官网及内容平台）
→ 官网直接发布 / 本地助手分平台执行
→ 效果监测（问题、平台样本、提及、推荐和引用证据）
→ 内容缺口回流选题中心 / 事实错误回流企业知识
```

效果监测是发布后的证据采样与缺口回流环节，不是独立的数据大屏。GEOFlow 与 GEORank 当前源码不包含完整的多 AI 平台采样引擎，0.4 页面中的监测任务、趋势和样本均为新增能力与演示数据。

## 后台导航

1. 工作台：只展示可行动待办、当前阶段和快捷入口。
2. 选题中心：业务线关键词、问题词库、选题库、内容计划和归档管理（归档问题 / 归档选题）。历史词包只记录单次 GEORank 拓展，不替代长期关键词库。
3. 内容生产：三级入口为 AI 创作台、文章任务和写作智能体；共同使用生成记录、逐条知识引用、版本快照、编辑审核和内容风控。
4. 发布运营：账号组选择、发布任务和分平台结果。
5. 效果监测：监测概览、问题样本、引用信源和监测任务。
6. 官网运营：官网预览、首页编排、内容栏目、线索和站点设置。
7. 企业知识：我的知识库（文档库/问答库）、业务线知识包、企业事实、待审核、知识缺口、品牌图库和内容规则。
8. 发布助手：设备、账号组、平台登录状态和配对。
9. 系统设置：模型、成员权限、日志、版本和数据维护。

站点诊断属于低频配置，仅放在「官网运营 → 站点设置 → 站点状态」，不占用日常主导航入口。

## 选题中心数据链

```text
BusinessLine（产品 / 业务线）
  └─ ManagedKeyword（长期维护的种子词和拓展词）
       ├─ KeywordPack（一次 GEORank 拓展记录）
       └─ QuestionLibraryItem（标准客户问题）
            └─ TopicCandidate（人工确认的正式选题）
                 └─ ContentPlan（完成日期、负责人、形式、知识范围、写作智能体快照和可选平台写作提示）
                      └─ Article（内容生产任务与生成快照）
```

这条链只描述“按计划生产”。计划文章必须保存 `topic_id` 与 `content_plan_id`，不能从临时拓词结果直接跳过人工确认生成文章。直接创作使用另一条明确的数据链：

一次关键词拓展按语义拓展、场景覆盖、商业意图、推荐榜单、产品评测、品牌关联、问答长尾和技术方案八个栏目组织候选，每个栏目固定生成 5 个问题，总计 40 个。多个种子词在这 40 个问题中轮换使用，不按种子数成倍放大。拓展结果、问题词库和选题库都提供限定当前可见范围的全选 / 取消全选，不能跨业务线或跨隐藏栏目修改选择状态。

拓展结果中的 `candidate` 仅是待确认候选，允许在当前栏目单条或批量删除；已经进入问题词库的 `active` 问题不受候选删除影响。删除会记录词包级抑制计数，避免下一次迁移或刷新时自动补回用户明确移除的候选。

四个运营列表按“待处理队列”展示：候选确认进入问题词库后从关键词拓展待处理列表隐藏；问题生成正式选题后从问题词库隐藏；选题加入内容计划后从选题库隐藏。历史对象不物理删除，仍通过内容计划、文章和引用关系保留可追溯记录。

```text
BusinessLine
  └─ WritingWorkspace（直接创作上下文，content_plan_id = null）
       ├─ AIConversation / AIProposal
       ├─ ContentAsset
       └─ GenerationRun
            └─ Article（topic_id 可空，但必须保存 topic_snapshot）
```

两条链的所有对象都必须保存 `business_line_id`。直接创作不能为了复用计划接口而创建空白或隐藏的 `ContentPlan`；工作区必须保存用户输入的主题快照和来源。业务线切换时只展示本业务线的数据，批量操作不能混入隐藏的其他业务线对象。

业务线删除采用“空记录物理删除、有历史数据则可恢复归档”的策略，并且每个客户空间至少保留一条启用业务线。归档后停止新的关键词拓展、内容生成、知识检索、监测与发布任务；历史计划快照、文章、发布结果、知识版本和引用证据必须继续可读，恢复业务线时重新启用其专属知识库与日常运营入口。

## 问题与选题管理、归档和版本

问题词库和选题库都采用 `active / archived` 管理生命周期。只有 `active` 记录可以被选中、生成新选题、加入新内容计划或发起新的文章生成；`archived` 记录只在「选题中心 → 归档管理」中展示，并按“归档问题”和“归档选题”分开管理。归档时记录 `archived_at`、`archived_by` 和 `archived_reason`，恢复后重新变为 `active`。

- 归档是可恢复操作，不删除来源关系。已归档问题或选题仍可从历史计划、文章及引用详情中查看，但不能进入任何新建计划或新的直接生成流程。
- 问题与选题独立归档，不做隐式级联。归档问题不会自动归档其选题，归档选题也不会改变来源问题；下游对象继续显示创建时的来源快照。
- 只要问题仍关联选题、计划或文章，或者选题仍关联计划或文章，就禁止永久删除，只能归档。来自 `KeywordPack` 的问题还承担拓词来源审计，演示版不提供永久删除；只有人工录入且没有任何下游引用的记录允许永久删除。
- 编辑问题或选题必须递增 `version` 并保留修改时间、修改人和变更说明。不能原地覆盖历史版本，也不能用新标题、问题描述或分类静默回写已有计划与文章。
- 创建选题时冻结 `question_snapshot`；创建内容计划时冻结每个入选项的 `topic_snapshot`；创建文章和 `GenerationRun` 时再次保存 `topic_snapshot`。计划创建后，即使原选题被编辑或归档，尚未执行的该计划仍按计划内快照继续生成；归档只阻止它进入新的计划。

正式数据模型不应把问题与选题长期限制为一对一。建议使用显式关联表支持一个问题拆成多个写作角度，以及一个选题综合多个客户问题：

```text
QuestionLibraryItem
  └─ QuestionVersion（不可变版本）
       └─ QuestionTopicLink（question_id + question_version_id + topic_id + relation_type）
            └─ TopicCandidate
                 └─ TopicVersion（不可变版本）
                      ├─ ContentPlanTopic（topic_version_id + topic_snapshot）
                      └─ Article（topic_id + topic_snapshot + generation_snapshot）
```

`QuestionTopicLink` 必须保存租户、业务线、关联时使用的问题版本、创建人和创建时间。展示引用关系时从关联表计算问题 → 选题 → 计划 → 文章的链路；归档状态只控制新流程可用性，不改变或删除已经存在的关联行。

## 企业知识模型与绑定策略

企业知识按“内容类型”和“使用范围”两条轴组织。文档库与问答库是业务类型；RAG 与 Wiki 是底层索引策略，两者不能混成同一个选择项。

```text
Tenant
  ├─ KnowledgeLibrary（type=document）
  │    └─ KnowledgeDocument
  │         └─ KnowledgeDocumentVersion（审核发布版本）
  │              └─ KnowledgeChunk（RAG 检索片段）
  ├─ KnowledgeLibrary（type=qa）
  │    └─ KnowledgeQA
  │         └─ KnowledgeQAVersion（审核发布版本）
  └─ KnowledgePackage
       ├─ KnowledgePackageItem（知识库 / 文档 / 问答）
       └─ BusinessLine.default_knowledge_package_id
```

- 文档库保存 PDF、Word、Excel、网页、产品资料、案例和资质等长资料；问答库保存标准问题、官方答案、异议处理和对外服务边界。
- 企业公共知识包可以被所有业务线继承；每条业务线另外绑定一个默认知识包，避免每篇文章反复选择相同资料。
- `ContentPlanKnowledgeScope` 从业务线默认知识包复制出一份计划级范围，可明确增补或排除知识库、文档、问答；计划发布为内容任务时保存不可变范围快照。
- `ContentPlan.writing_hints.expected_platform_ids` 是可空的写作提示，只影响生成时的结构、段落和表达节奏；它不能预建、锁定或默认勾选发布目标，也不能替代发布阶段的账号组与平台选择。
- 只有状态为 `approved/published` 的知识版本可参与写作；草稿、待审核、冲突或已废止版本不得召回。
- 知识包只保存选择规则，不复制正文。生成时解析成确切知识版本，避免资料更新后历史文章证据被悄然替换。
- 首期统一使用 RAG：文档解析、切块、向量化并在当前租户命名空间内混合检索。Wiki 知识图谱放在后续版本，用于实体关系与多跳检索；Wiki 中的每个事实仍必须指回已审核来源，不能成为无来源的新事实。

## 写作智能体、知识库与模型设置

三者各自承担一个明确职责，不能用一个全局提示词混在系统设置里：

```text
写作智能体（怎么写）
  ├─ 写作角色、语气与风格
  ├─ 内容结构与输出模板
  ├─ 系统提示词与约束规则
  └─ 知识召回偏好及严格知识模式

企业知识库（依据什么写）
  └─ 已审核事实、标准问答、产品资料、案例、资质和对外边界

模型设置（用什么执行）
  └─ 模型供应商、模型版本、凭据、超时、用量和底层生成参数
```

系统设置只管理模型执行能力，不再保存唯一的全局写作提示词。模型设置不能扩大知识范围或改写智能体版本；切换底层模型时，生成记录必须保存实际供应商、模型版本和参数。

### 数据模型与版本规则

```text
WritingAgent
  └─ WritingAgentVersion（不可变版本）
       ├─ role / tone / style / template
       ├─ system_prompt / strict_knowledge
       ├─ applicable_business_lines / content_types
       └─ preferred_knowledge_base_ids

BusinessLine.default_writing_agent_id
ContentPlan.writing_agent_id
ContentPlan.writing_agent_snapshot
WritingWorkspace.writing_agent_id
WritingWorkspace.writing_agent_snapshot
GenerationRun.generation_snapshot
Article.generation_snapshot
```

- 内置智能体由产品提供，租户运营人员不能直接修改或删除；可以复制成自定义智能体，再按企业需要配置。
- 自定义智能体的每次有效修改都创建新的 `WritingAgentVersion`。版本内容不可原地覆盖，名称、创建人、创建时间、变更说明和版本号进入审计记录。
- 停用智能体只会从新计划的可选项和业务线默认项中移除。历史计划、生成记录和文章继续通过快照展示当时配置；被历史对象引用的版本不能物理删除。
- 业务线默认智能体只是新计划的默认选择。运营人员可以在适用范围内改选，最终以计划保存的 `writingAgentSnapshot` 为准。

`writingAgentSnapshot` 至少冻结智能体 ID、名称、版本、角色、风格、结构、系统提示词、严格知识模式、适用范围和知识召回偏好。它是内容计划或直接创作工作区的写作契约，智能体后续升级或停用都不能让既有计划、工作区或文章静默漂移。

每次实际生成再创建 `generationSnapshot`，冻结本次使用的计划或工作区智能体快照、实际模型及参数、提示词渲染结果、本次知识范围、命中的知识版本 / 片段和生成时间。`GenerationRun` 保存完整执行记录，文章保存一份对应快照引用或不可变副本，保证编辑器和审核页能解释“这篇文章当时如何生成”。

### 计划与文章流程

```text
业务线默认智能体
→ 创建内容计划时选择一个启用且适用的智能体
→ 预览角色、风格、文章结构、智能体版本和知识规则，可选补充预计适配平台写作提示
→ 创建内容任务时冻结 ContentPlan.writingAgentSnapshot
→ 在计划知识范围内检索已审核资料
→ 新建 GenerationRun 并冻结 generationSnapshot
→ 生成或更新文章，同时保留知识引用
→ 风控、人工审核并冻结 ArticleVersionSnapshot
```

文章编辑器允许选择另一个启用且适用的智能体重新生成，但必须新建 `GenerationRun` 与新的文章 `generationSnapshot`，旧生成记录、旧文章版本和旧引用证据继续保留。切换智能体不能沿用失效的风控与审核结果；新正文回到待检测、待审核状态。只编辑正文而不重新生成时，也不能伪造或重写原 `generationSnapshot`。

内容生产默认使用“计划任务”视图：先按 `ContentPlan` 汇总选题数量、文章创建进度、审核和发布状态，再进入计划查看全部文章任务。文章任务列表保留“全部文章”辅助视图，并支持按 `plan_id` 筛选；直接创作的文章使用独立的“直接创作（无计划）”分组，不计入任何计划进度。计划入口不能只打开第一篇文章，必须展示该计划下的完整任务集合；尚未生成文章的选题也要以“未生成”任务占位，并允许从计划详情继续生成。进度按计划选题的唯一 `topic_id` 覆盖率计算，重复文章或额外文章单列，不得伪造完成率。

## AI 创作台与协作对话

AI 创作台是内容生产的直接创作入口，不等同于“快速创建一条内容计划”。正式模型使用 `writingWorkspaces + aiConversations + contentAssets` 承载未完成上下文、对话提案与素材：

```text
WritingWorkspace
  ├─ business_line_id + business_line_snapshot
  ├─ topic_id（可空）+ topic_snapshot（必填）
  ├─ writing_agent_id + writing_agent_snapshot
  ├─ WorkspaceKnowledgeScope + locked_knowledge_versions
  ├─ AIConversation
  │    └─ AIMessage
  │         └─ AIProposal（结构 / 标题 / 正文 / 图片建议）
  └─ ContentAsset
       ├─ temporary_attachment
       ├─ generated_image
       └─ knowledge_image
```

创建工作区时先选择业务线；首次生成时冻结业务线名称与边界、用户输入或选中的主题、智能体版本、本次知识范围及实际命中的知识版本。生成出的文章保持 `content_plan_id = null`，并通过 `writing_workspace_id` 与 `GenerationRun` 追溯来源。后续修改业务线、主题、智能体或扩大知识范围都必须显式产生新的生成或文章版本，不能静默改变旧快照。

左侧创作区使用标题输入 + 可编辑正文画布，允许运营人员直接写作和修改文章文字；空白工作区左侧不重复放置 AI 生成表单。手工内容可以直接保存为文章草稿，但在完成知识映射前不得伪造引用或通过审核。右侧对话是新文章写作入口，用户发送写作要求后生成带快照的初稿。右侧 AI 对话只产生建议和 `AIProposal`，不能在模型返回时直接覆盖编辑器。运营人员查看结构或正文差异并点击应用后，系统才创建新的文章版本、记录应用人和 proposal ID，并将风控、引用核验与人工审核状态重置为待处理；拒绝的 proposal 仍可保留在对话审计中，但不会改变正文。

创作台底部工具具有不同的权限与证据语义：

- 写作智能体控制当前对话和提案的写法；每次执行保存所选智能体快照，不能用下拉框改写历史消息。
- 联网搜索结果保存 URL、标题、抓取时间和摘要，只能作为外部参考。未经企业知识入库、审核和版本发布，不得支撑企业能力、案例、价格、资质或效果承诺。
- 临时附件属于当前工作区的会话上下文，保存文件哈希、上传人、有效期和解析结果；默认不进入企业知识，也不能生成正式 `ArticleCitation`。需要长期复用时必须显式导入知识库并通过审核。
- 引用知识库 / 文件时，只能选择当前租户与业务线授权范围内的已审核版本；应用 proposal 时把实际使用的版本和片段写入知识快照及 `ArticleCitation`。
- 知识库图片必须作为版本化 `ContentAsset` 保存原素材、缩略图、版权 / 授权信息、可见范围和来源知识对象。插入图片不等于证明正文事实，文字判断仍需独立的已审核知识引用。

桌面端采用正文编辑区与右侧 AI 对话双栏布局。宽度不足时切换为「正文 / AI 对话 / 文章信息」三个互斥页签；三个页签共享同一个工作区草稿、所选智能体和上下文，切换时不得重建会话或丢失未保存内容。

### 知识权限边界

写作智能体的知识配置是“排序偏好”，不是“授权清单”。一次生成可检索的有效范围必须是以下条件的交集：

```text
当前 tenant_id
∩ 当前业务线允许范围
∩ ContentPlanKnowledgeScope 或 WorkspaceKnowledgeScope 冻结范围
∩ approved / published 的确切知识版本
```

- `preferred_knowledge_base_ids` 只能在上述交集中提高召回优先级，不能把计划或工作区排除的资料重新加入，也不能读取其他租户或其他业务线的专属资料。
- 智能体即使绑定了某个知识库，只要该库未进入计划 / 工作区范围、版本未审核或已废止，本次生成就不能召回。
- 运营人员切换智能体不会自动扩大知识范围；需要补充资料时，必须按内容计划或创作工作区权限显式修改范围并留下新快照或修订记录。
- 严格知识模式下，关键事实没有足够证据、来源冲突或已过期时必须返回知识缺口，不能用模型常识补成确定性企业事实。
- 模型供应商、系统管理员和后台队列都必须执行同一知识边界，不能通过手工提示词、重试或降级模型绕过。

## 内容生成与证据链

正式生成链路必须同时记录“为什么生成这篇文章”和“文章中的企业事实来自哪里”。

```text
ContentPlan + ContentPlanKnowledgeScope + writingAgentSnapshot
                         或
WritingWorkspace + WorkspaceKnowledgeScope + writingAgentSnapshot
                         ↓
GenerationRun（一次生成执行与 generationSnapshot）
  ├─ GenerationKnowledgeSnapshot（实际使用的知识版本与检索片段）
  └─ Article（当前可编辑稿与本次 generationSnapshot）
       ├─ ArticleCitation（正文片段 ↔ 知识证据）
       └─ ArticleVersionSnapshot（应用提案 / 审核 / 发布时冻结）
```

`GenerationRun` 至少保存租户、业务线、选题或主题快照、可空的内容计划、可空的创作工作区、写作智能体快照、实际模型、渲染后提示词、参数、知识范围快照、检索结果、生成状态、耗时、输入/输出用量和失败原因。重新生成必须新建记录，不能覆盖旧执行。文章的 `generationSnapshot` 与该记录关联，智能体或模型设置后续变化不能改写历史文章的生成依据。

`ArticleCitation` 至少保存文章、生成记录、正文段落定位、知识库、来源类型、来源对象、知识版本、引用原文、页码/章节/URL、相关度和人工核验状态。引用不是仅供展示的“共 6 条”，编辑器必须能从文章段落追溯到原文证据。

`ArticleVersionSnapshot` 在应用 AI proposal、提交审核和创建发布任务时冻结文章正文、标题、摘要、引用列表、知识版本、风险扫描结果和内容哈希。应用 proposal 或其他正文修改会产生新版本并使旧扫描、引用核验和审核结果失效；已经排队或发布的任务仍引用原快照，不能被当前草稿替换。

当检索结果不足、来源互相冲突或关键事实过期时，生成任务应返回知识缺口并阻止模型补写确定性企业事实。运营人员补充并审核知识后，再创建新的 `GenerationRun`。

## 内容风控状态

内容风控直接复用 GEOFlow 的规则与门禁语义，不使用没有源码依据的“风险分”。

```text
unscanned → 尚未检测（界面状态）
stale     → 正文或规则变化，旧结果已过期（界面状态）
clean     → 未命中规则，可以继续审核和发布
warning   → 命中警告规则，需要修订；正式版可由管理员填写原因后覆盖
blocked   → 命中阻断规则，必须修改，不能人工覆盖
```

扫描结果绑定当前文章内容和词典哈希。文章修改后必须重新扫描；发布只允许使用已审核、风控为 `clean` 且被冻结的文章版本。

## 效果监测数据边界

正式版应将监测定义、执行轮次和单个平台样本分开保存：

```text
MonitorQuestion（监测问题与业务线）
  └─ MonitorRun（同一问题集、平台和入口的一轮执行）
       └─ MonitorSample（单问题、单平台的原回答与证据）
```

单个样本至少保留问题、平台、入口、模型版本、采样时间、原始回答、是否提及、是否明确推荐、榜单内排名、引用 URL、竞品和人工核验结果。趋势只能比较相同问题集、平台和入口的不同轮次。

## 发布安全与一致性

- 一个账号组在同一平台只绑定一个账号。
- 同一篇文章不会同时发布到同一平台的多个账号。
- 一篇文章每个平台只生成一个有效发布目标，服务端使用幂等键防止重复任务。
- 发布任务冻结文章版本；文章修改后需要创建新版本，不能替换待发布内容。
- 各平台独立执行、独立重试，一个平台失败不影响其他平台。
- 平台提交后断网时标记为「结果待核验」，不能直接盲目重发。
- 本地助手只主动发起 HTTPS 请求，服务器不反向连接客户电脑。
- 服务端只保存设备、账号别名、平台类型、可用状态和结果，不保存平台登录凭据。

## 生产底座与后续交付边界

当前工程已经落地的底座能力：

- SQLite 单机数据库：迁移表、WAL、外键、忙等待、工作区修订和乐观锁。
- 内部账号体系：首次管理员初始化、Cookie Session、CSRF、scrypt 密码摘要、四级角色权限、成员管理和审计日志。
- 配置安全：模型 API Key 使用 AES-256-GCM 加密保存；发布器 Token 与设备密钥只保存摘要，旧版明文状态会在读取时迁移。
- 运行运维：`/health/live`、`/health/ready`、Docker / Compose、Nginx 参考配置、备份与恢复脚本、生产 API 自动化检查。
- 业务边界：服务端工作区 API 是最终数据源；发布器配对、会话同步、平台任务和审核门禁已经有明确接口。

尚需在底座之上逐步接入的业务实现：

- 企业知识的 PDF/Office 专用解析器、OCR 队列、版本化知识资产、异步索引/重试和可插拔外部向量数据库适配已接入；私有化部署时仍需配置实际 OCR 服务或远程向量后端。
- 官网 CMS 的页面、栏目、文章发布与公开信源同步。
- 效果监测的真实多平台采样、原回答存证、引用统计和趋势任务。
- 各内容平台的真实浏览器自动化适配、验证码/风控处理和发布结果核验。

这些后续模块都必须复用当前账号权限、工作区版本、审计、知识范围和发布快照规则，不能重新建立一套绕过生产底座的演示数据通道。
